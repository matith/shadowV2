# Personal Ledger Taxonomy

多账本，而不是一个巨大 Memory。不同信息的 **价值、生命周期、访问方式** 不同，由不同 Ledger / Memory Expert 负责。

模型（经 Ledger Router）判断信息应进入哪些账本。**允许一条消息同时关联多个 Ledger**，用引用连接，不复制原文。

---

## 1. Daily / Event Ledger

**职责：** 记录“发生了什么”。

**典型内容：**

- 日常事件、对话结果、临时事项
- 承诺（我答应 / 别人答应）
- 进展、跟进、状态变化消息

**特征：** 强时间属性；Event 是历史流，不等于 Matter 当前状态。

---

## 2. Matter Ledger

**职责：** 持续事项的 **当前状态**。

**典型事项：** 春促启动会、某合同、某采购、拾光 V2、长期项目。

**实体能力：**

- 当前状态、当前摘要、目标、下一步
- 子事项（树状层级）
- 关联事件 / 人物 / 资料 / 附件
- 截止时间、提醒、历史状态、生命周期

**注意：** 不是传统二维表；UI 上可投影成表格，但结构支持父子层级。

---

## 3. Knowledge Ledger

**职责：** 较稳定长期知识。

**典型内容：** 工作制度、公司流程、政策、常用方法、技术知识、个人长期经验。

**访问：** 不默认进上下文；相关问题出现时再读取。

---

## 4. Product / Business Ledger

**职责：** 重要产品与业务资料。

**典型内容：** 产品说明、手册、资费政策、管控通知、营销政策、技术参数、FAQ、版本资料。

**边界：** 不与“今天给谁回电话”混在同一短期 Memory。

---

## 5. People / Relationship Ledger

**职责：** 长期存在的人和关系。

**典型字段：** 姓名、单位、角色、与用户关系、相关 Matter、最近互动、承诺、长期备注。

**目的：** 避免每次事项都重新理解同一个人。

---

## 6. File / Source Ledger

**职责：** 原始资料的位置与可追溯性。

**覆盖：** 文档、PDF、PPT、Excel、图片、消息、网页、上传附件、Agent 工具结果。

**核心问题：** “原文到底在哪里？”

---

## 7. Directive / Policy Ledger

**职责：** 用户长期规则，不是普通事实。

**例子：**

- 晚上十点后不要主动提醒工作事项
- 客户经理资料优先归工作知识库
- 除非明确说保存，否则闲聊不长期记录
- 涉及合同金额的内容不要自动修改

Agent 行动前应读取相关 Directive。

---

## 8. Archive Ledger

**职责：** 完成或长期不活跃事项的极小召回层。

**规则：**

- 归档 ≠ 删除
- 保留极小 Archive Capsule + 指向完整 Matter / Event / Source 的指针
- 用户数月后提起时，先命中极小摘要，再按需展开完整历史

---

## 9. 路由示例

| 用户输入 | 可能落入 |
| --- | --- |
| 明天提醒我给李经理打电话 | Daily / Matter / Reminder |
| 这是公司最新的云电脑产品政策 | Product / Knowledge / File |
| 王经理已经调到市场部了 | People |
| 把这份 PDF 存起来以后查 | File / Knowledge |
| 项目已经彻底结束 | Matter → Archive |

Router 不需要绝对准确；信息可多账本关联。
